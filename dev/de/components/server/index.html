Komponenten
Server

Server

claimward-vpn-server: prüft die Anmeldung, vergibt VPN-Adressen, programmiert das WireGuard-Gateway, streamt die Routen der Mandanten über gRPC und stellt eine Admin-API und Metriken bereit.

claimward-vpn-server v0.14.0 ist die Steuerungsebene. Er prüft das Bearer-Token, das ein Gerät vorlegt, vergibt VPN-Adressen und programmiert das WireGuard-Gateway mit einem Peer pro registriertem Gerät. Er läuft auf dem Gateway-Host, neben einem vorhandenen wg0: Linux (nftables) oder, ab v0.10.0, OpenBSD (pf, siehe OpenBSD).

Die API-Anfragen tragen Authorization: Bearer <token>: ein GitHub-Access-Token, ein OIDC-ID-Token oder ein go-authn-Access-Token, je nach dem Anbieter, den sie im Header Claimward-Provider nennen (seit v0.14.0, siehe Identitätsanbieter). Die Nutzdaten sind im Registrierungsprotokoll beschrieben.

Mit TLS_CERT und TLS_KEY verwenden beide Listener TLS. Ohne sie ist die HTTP-API unverschlüsselt (terminieren Sie TLS an einem Proxy), ebenso der RouteService, den die Clients dann ablehnen, außer über Loopback: Geräte verbinden sich, erhalten aber keine Live-Aktualisierungen der Routen.

Credentials

Jedes Secret ist eine Datei im Verzeichnis, das CREDENTIALS_DIRECTORY nennt, nie eine Umgebungsvariable: Eine Umgebung wird in jeden Kindprozess und jeden Crash-Dump kopiert. systemd setzt die Variable für LoadCredential= und LoadCredentialEncrypted=; auf den anderen Plattformen setzen Sie sie selbst. Die Dateinamen sind fest, ein abschließender Zeilenumbruch wird entfernt.

DateiErforderlichInhalt
wg-private-keyimmerder private Schlüssel des Gateways in Base64
admin-tokenneinBearer-Token der Admin-API und der WebUI; ohne die Datei sind sie deaktiviert
provider-<id>-gateway-secretein go-authn-Anbieterdas Secret des Gateway-Clients (war goauthn-gateway-secret, vor v0.14.0)
provider-<id>-secretjeder github-Anbieterdas Client-Secret der GitHub-OAuth-App dieses Anbieters (siehe github_client_id; war github-client-secret, vor v0.14.0)
github-tokenwenn ein Mandant members hatBearer für GET /users/{login} (siehe Mandanten)

Eine fehlende erforderliche Datei verhindert den Start und wird benannt. Vor dem Lesen prüft der Server jede Datei über den offenen Deskriptor (O_NOFOLLOW, dann fstat) und verweigert einen symbolischen Link, alles außer einer regulären Datei, eine für Gruppe oder andere lesbare Datei, eine Datei, die nicht der UID des Servers gehört, eine leere Datei und eine über 64 KiB. Eine Ausnahme seit v0.7.1: Eine Datei der UID 0 mit genau dem Modus 0440 wird akzeptiert, wenn ihre Gruppe die GID des Servers oder eine seiner Zusatzgruppen ist (so ein Kubernetes-Secret-Volume mit fsGroup). Eine zweite seit v0.9.0, für systemd mit DynamicUser=yes: systemd lässt die Datei root:root, Modus 0400, plus einen schreibgeschützten POSIX-ACL-Eintrag für die UID des Dienstes (src/core/exec-credential.c:338-361, src/shared/acl-util.c:448-494), sodass stat 0440 zeigt. Der Server liest system.posix_acl_access vom offenen Deskriptor und akzeptiert genau user:: (ohne Schreiben oder Ausführen), user:<seine UID>:r--, group::---, mask::r--, other::---; jeder andere benannte Benutzer oder jede Gruppe, jedes Schreib- oder Ausführungsbit und ein fehlerhafter oder zu großer Wert werden abgelehnt. Die Fehlermeldung nennt die Abhilfe.

Die Organisationsprüfung des Anbieters github verwendet github-token nicht: Sie läuft mit dem Token der Person, ein privates Mitglied ist also nur sichtbar, wenn dieses Token read:org trägt. Die Credential ist optional, solange nur Organisationen verwendet werden.

Migration von v0.5.0 (inkompatibel). ADMIN_TOKEN, WG_PRIVATE_KEY, WG_PRIVATE_KEY_FILE und GOAUTHN_GATEWAY_SECRET_FILE werden nicht mehr gelesen, und der Server verweigert den Start, solange eine davon gesetzt ist; er nennt die anzulegende Datei. Legen Sie jeden Wert in seine Datei (admin-token, wg-private-key, goauthn-gateway-secret), entfernen Sie die Variable und setzen Sie CREDENTIALS_DIRECTORY. Ein Mandant mit members braucht jetzt auch github-token.

Identitätsanbieter

Seit v0.14.0 akzeptiert der Server mehrere Identitätsanbieter gleichzeitig. Sie stehen in der JSON-Datei, die PROVIDERS_FILE nennt (unbekannte Felder werden abgelehnt, höchstens 1 MiB):

{"providers":[
  {"id":"campus","kind":"oidc","name":"Campus","oidc_issuer":"https://idp.example.org","oidc_client_id":"claimward"},
  {"id":"hub","kind":"github","name":"GitHub","github_client_id":"Iv1.0123456789abcdef","allowed_orgs":["my-org"]}
]}
kindFelder außer id, kind, nameSecret-Datei
githubgithub_client_id, api_url (GitHub Enterprise), allowed_orgsprovider-<id>-secret
oidcoidc_issuer, oidc_client_id, allowed_domainskeine
go-authnoidc_issuer, oidc_client_id, gateway_client_idprovider-<id>-gateway-secret
  • github: Das Bearer-Token ist ein GitHub-OAuth-Access-Token aus dem Device Flow. Der Server fragt GitHub (Check a token) mit dem Secret des Anbieters, bevor er ihm traut, sodass nur Token dieser OAuth-App zugelassen werden, löst es dann über die GitHub-API auf (/user, /user/orgs) und lässt ein aktives Mitglied einer der allowed_orgs oder ein benanntes Mandantenmitglied zu (die Liste ist nur optional, wenn ein Mandant members hat). Ohne Client-ID, ohne Secret-Datei oder ohne Allowlist und benannte Mitglieder: Der Server startet nicht, es gibt keine Ausnahme-Option.
  • oidc: Das Bearer-Token ist ein OIDC-ID-Token, geprüft gegen den Issuer mit der Audience oidc_client_id und der optionalen allowed_domains (die E-Mail des Tokens muss verifiziert sein).
  • go-authn: Das Bearer-Token ist ein Access-Token (at+jwt) eines go-authn/bridge-Anbieters, und der Schlüssel des Geräts muss dort von derselben Person registriert sein. Der Server liest die signierte Liste der registrierten Schlüssel des Anbieters (go-authn/wireguard) und entfernt aus wg0 einen Schlüssel, den der Anbieter zurückzieht. Höchstens ein Anbieter ist von dieser Art.

Die Anfrage nennt ihren Anbieter. Jeder API-Aufruf trägt den Header Claimward-Provider: <id> (gRPC: die Metadaten claimward-provider), und sein Token wird von diesem Anbieter allein beurteilt: Ein Token des Anbieters A wird abgelehnt, wenn die Anfrage B nennt. Kein Header ist 401 missing_provider, eine Id, die der Server nicht listet, ist 401 unknown_provider. Das Discovery-Dokument listet die Anbieter (nie ein Secret), sodass ein Client nur die URL des Servers braucht.

Eine Identität pro Issuer und sub. Die Identität ist issuer#sub für oidc und go-authn und github:<id> für github: Dasselbe sub bei zwei Issuern sind zwei Personen, und die zweite kann das Gerät der ersten nicht übernehmen.

Mandanten. Ein Mandant erhält ein Feld providers, und seine Gruppen werden <Anbieter-Id>:<Gruppe> geschrieben. Bei mehreren Anbietern muss ein Mandant, der domains oder idps verwendet, providers nennen, sonst schlägt der Server geschlossen fehl (fail closed).

Umstieg auf v0.14.0 (inkompatibel). AUTH_PROVIDER, OIDC_ISSUER, OIDC_CLIENT_ID, OIDC_ALLOWED_DOMAINS, GITHUB_CLIENT_ID, GITHUB_ALLOWED_ORGS und GOAUTHN_GATEWAY_CLIENT_ID werden nicht mehr gelesen, und der Server verweigert den Start, solange eine gesetzt ist; er nennt die Datei, die sie ersetzt. Schreiben Sie die Anbieterdatei, benennen Sie github-client-secret in provider-<id>-secret und goauthn-gateway-secret in provider-<id>-gateway-secret um, schreiben Sie die Mandantengruppen als <Anbieter-Id>:<Gruppe>, und rechnen Sie mit einem neuen Subject für jede Person (issuer#sub, github:<id>), sodass sich die Geräte neu registrieren. Verwenden Sie Client v0.9.0 oder neuer: Ältere Clients senden den Header nicht.

Jeden Ablauf von Ende zu Ende finden Sie unter Identitätsanbieter.

Registrierungsregeln

  • Ein Schlüssel gehört demjenigen, der ihn registriert hat. Das Registrieren eines Schlüssels, den eine andere Identität hält, wird abgelehnt (409 key_taken): Ein öffentlicher Schlüssel ist öffentlich, und ihn zu übernehmen gäbe die Macht, das Gerät seines Besitzers abzumelden.
  • Derselbe Schlüssel, erneut von seinem Besitzer registriert, behält seine Adresse und erhält eine neue Lease.
  • Die einzige erlaubte IP des Peers ist das /32 des Geräts, sodass Geräte die Adressen der jeweils anderen nicht verwenden können.
  • Der Mandant ist derjenige, den der Aufrufer angefordert hat, sofern er Mitglied ist, oder sein einziger. Siehe Mandanten.

Wie er das Gateway programmiert

Der Server verwendet wgctrl, um Peers auf einer vorhandenen Schnittstelle hinzuzufügen und zu entfernen, und prüft beim Start, dass die Schnittstelle existiert. Die Schnittstelle selbst (ihr privater Schlüssel und Listen-Port) bleibt wg-quick oder systemd-networkd beim Booten überlassen, was die privilegierte Einrichtung der Schnittstelle aus dem dauerhaft laufenden Dienst heraushält.

OpenBSD (pf)

Ab v0.10.0 läuft der Server auch unter OpenBSD und setzt die Zugriffsrichtlinie dort mit pf statt mit nftables durch. Er spricht den Kernel direkt über die ioctls von /dev/pf an; er startet nie pfctl, und es gibt keinen Rückfall auf pfctl.

  • Unterstützte Versionen: OpenBSD 7.9 und 8.0. Sie teilen sich dasselbe Layout von struct pf_rule, das der Server gegen die laufende Version prüft. Auf jeder anderen Version startet der Server nicht, statt eine Regel falsch zu kodieren.

  • pf.conf gehört Ihnen. Der Server ändert den Hauptregelsatz nie. Fügen Sie /etc/pf.conf eine Zeile hinzu und lassen Sie pf aktiviert:

    anchor "claimward"

    Der Server lädt die Richtlinie in diesen Anchor. Beim Start liest er den Hauptregelsatz zurück und prüft, dass er anchor "claimward" aufruft.

  • Er startet nicht, wenn /dev/pf nicht lesend und schreibend geöffnet werden kann (er muss als root starten), wenn pf deaktiviert ist, wenn der Hauptregelsatz den Anchor nicht aufruft (die Richtlinie würde geladen, ohne etwas zu filtern) und wenn pf.conf für die WireGuard-Schnittstelle (wg0, wg*) set skip on enthält, weil pf den Datenverkehr der Peers dann nie sähe.

  • Dieselbe Richtlinie wie unter Linux. Standardmäßig wird der auf WG_INTERFACE eingehende Verkehr verworfen; erlaubt ist nur IPv4, IPv6 durch den Tunnel wird verworfen. Die MSS-Begrenzung (TUNNEL_MTU) gilt für beide Familien, als Regel match ... scrub (max-mss N).

  • Atomar und fail-closed. Anchor und Tabellen werden in einer einzigen pf-Transaktion ersetzt, danach zurückgelesen und mit dem verglichen, was geladen werden sollte. Schlägt das fehl, wird ein vollständiges Verwerfen geladen. Der Anchor bleibt beim Beenden des Prozesses bestehen. Tabellennamen tragen ein Generationssuffix pro Ladevorgang, sodass das kurze Fenster zwischen dem Übernehmen der Tabellen und dem der Regeln nie die Regeln eines Mandanten auf die Peers eines anderen anwenden kann.

  • Rechtetrennung (ab v0.11.0). Das Versprechen pf von pledge(2) erlaubt nur zwölf der DIOC*-ioctls (sys/kern/kern_pledge.c, pledge_ioctl); der Server braucht zusätzlich DIOCRINADEFINE, DIOCXROLLBACK, DIOCGETRULES, DIOCGETRULE, DIOCXEND und DIOCRGETADDRS; jedes andere ioctl würde den Prozess beenden. Daher hat der Eltern-Prozess (root), der /dev/pf bedient, kein Pledge. Der unprivilegierte Kindprozess _claimward, der die Geheimnisse hält und das Netz bedient, wird vor dem Bedienen mit unveil(2) und pledge(2) eingeschränkt (siehe unten).

  • WireGuard-Peers (ab v0.11.0). Vor v0.11.0 scheiterte unter OpenBSD eine Anmeldung beim Hinzufügen des Peers zu wg(4) (Issue Nr. 79). Der Server schreibt Peers jetzt mit den ioctls SIOCSWG und SIOCGWG aus sys/net/if_wg.h und liest sie mit einem eigenen Dekoder zurück. In echten OpenBSD-7.9- und -8.0-amd64-VMs geprüft: Das Strukturlayout stimmt mit dem des C-Compilers überein, und Hinzufügen, Ersetzen, Entfernen und Aufräumen funktionieren auf einer echten wg(4)-Schnittstelle. OpenBSD auf arm64 wird nur cross-kompiliert, nicht auf einem Kernel ausgeführt.

Bereitstellung unter OpenBSD (rc.d)

Ab v0.10.1 liefert das Repository deploy/openbsd/ mit: ein rc.d(8)-Skript, ein environment.example, ein hostname.wg0.example und ein pf.conf.example.

  • Zwei Prozesse (ab v0.11.0). Die WireGuard-Peer-Konfiguration von wg(4) liegt hinter suser(9) (sys/net/if_wg.c), und /dev/pf ist nur durch seinen Geräteknoten geschützt, der root vorbehalten ist: pfopen (sys/net/pf_ioctl.c) prüft nichts weiter. OpenBSD hat keine privilegierte Gruppe, mit der ein unprivilegierter Benutzer das eine oder das andere dürfte; das Skript startet den Daemon daher als root (daemon_user="root"), und der Daemon teilt sich in zwei Prozesse. Der Eltern-Prozess (root) fügt Peers hinzu und entfernt sie, setzt die Tunnel-MTU und lädt den pf-Anchor; er liest kein Geheimnis, bedient kein Netz und macht nur /dev/pf per unveil(2) sichtbar. Das Kind, ausgeführt als Benutzer _claimward, hält die Geheimnisse, die TLS- und gRPC-Listener, den Identitätsanbieter und die Mandantenrichtlinie und wird vor dem Bedienen mit unveil(2) und pledge(2) (stdio rpath inet dns) eingeschränkt. Kann es die Rechte nicht abgeben, startet der Server nicht. Das Kind fragt den Eltern-Prozess über ein Socketpair, und dieser verweigert alles außerhalb des Adresspools (VPN_CIDR).
  • Der Benutzer _claimward muss existieren, und die Ports müssen größer als 1024 sein (die Vorgaben 8443 und 8444 sind es); um auf 443 zu bedienen, leiten Sie mit einem pf-rdr-to um.
  • Geheimnisse sind Dateien in /etc/claimward/credentials, einem Verzeichnis 0700 im Besitz von _claimward, jede Datei 0400 und im Besitz von _claimward (install(1)). Das Skript setzt CREDENTIALS_DIRECTORY darauf; kein Geheimnis steht in der Umgebung, in Argumenten oder in einer URL. Die nicht geheimen Einstellungen stehen in /etc/claimward/environment, die root gehört.
  • wg0 muss existieren, bevor der Server startet: hostname.wg0 enthält denselben privaten Schlüssel wie das Geheimnis wg-private-key (Modus 0640).
install -m 0555 claimward-server /usr/local/bin/claimward-server
useradd -g =uid -c claimward -d /var/empty -s /sbin/nologin -r 1..999 _claimward
install -d -m 0755 -o root -g wheel /etc/claimward
install -d -m 0700 -o _claimward -g _claimward /etc/claimward/credentials
install -m 0400 -o _claimward -g _claimward wg-private-key /etc/claimward/credentials/wg-private-key
install -m 0600 -o root -g wheel environment.example /etc/claimward/environment   # dann bearbeiten
install -m 0640 -o root -g wheel hostname.wg0.example /etc/hostname.wg0           # dann bearbeiten
sh /etc/netstart wg0
install -m 0555 claimward_server /etc/rc.d/claimward_server
rcctl enable claimward_server
rcctl start claimward_server && rcctl check claimward_server

rcctl start meldet (ok) erst, wenn der Server auf LISTEN_ADDR Verbindungen annimmt; ein Daemon, der vorher endet, etwa an einem Geheimnis, das dem Konto _claimward nicht gehört, ergibt (failed).

Das Protokoll geht an syslog (/var/log/daemon). Die CI führt dieses Skript in echten OpenBSD-7.9- und -8.0-VMs aus: rcctl start, die Startzeile, rcctl check, ein Eltern-Prozess als root mit einem Kind _claimward, eine Anmeldung über das Kind, deren Peer auf wg0 erscheint, und rcctl stop; danach einen Start mit einem Geheimnis im Besitz von root und einen Start ohne den Anchor in pf.conf, die beide fehlschlagen müssen.

Bereitstellung unter s6 (sdcreds)

Ab v0.10.2 liefert das Repository deploy/s6/claimward-server/ (run und finish) für Hosts ohne systemd mit. sdcreds s6-run (go-authn/sdcreds v0.2.0 oder neuer) entschlüsselt jede Datei seines --source-Verzeichnisses in ein privates tmpfs, schreibt jede mit Modus 0400 und --user als Eigentümer, setzt CREDENTIALS_DIRECTORY und startet den Server unter diesem Benutzer. Eine Datei, die der UID des Prozesses gehört und für Gruppe und andere nicht zugänglich ist, ist die erste Form, die der Lader akzeptiert; er bleibt also unverändert. Kein Geheimnis geht durch die Umgebung, durch argv oder eine URL.

  • Eine Capability, absichtlich behalten. Der Server braucht CAP_NET_ADMIN (wgctrl, nftables, MTU der Schnittstelle). Standardmäßig leert s6-run alle Capability-Mengen des Dienstes und lässt no_new_privs aktiv; das Beispiel übergibt --keep-cap=CAP_NET_ADMIN, sodass der Server mit genau dieser einen Capability läuft (CapEff 0x1000). Sie wirkt auf den Netzwerk-Namespace, in dem der Supervisionsbaum läuft: den des Hosts, außer Sie starten s6-svscan in einem eigenen (ip netns exec).
  • Namen. Jede Datei von --source heißt wie ihr Geheimnis (wg-private-key, github-token, admin-token, provider-<id>-secret, provider-<id>-gateway-secret) und wird mit sdcreds encrypt --name=<dieser Name> verschlüsselt; jeder andere Name stoppt den Start. s6-run braucht root und CAP_SYS_ADMIN (es mountet ein Dateisystem).
  • Nicht geheime Konfiguration steht in /etc/claimward/env, das das run-Skript liest.
  • Container brauchen es nicht: Compose, Podman und Kubernetes mounten Geheimnisse bereits als Dateien (Tabelle oben).

Die CI führt dieses Verzeichnis unter einem echten s6-svscan aus, in einem Netzwerk-Namespace, mit einer echten WireGuard-Schnittstelle und nftables (kein Trockenlauf). Sie prüft, dass das Log den aus dem verschlüsselten Geheimnis abgeleiteten öffentlichen Schlüssel enthält (und keinen Kontrollschlüssel), dass der Server als Dienstbenutzer mit CapEff 0x1000 und no_new_privs läuft, dass kein Geheimnis in seiner Umgebung steht, dass eine Geheimnisdatei mit Modus 0644 abgelehnt wird und dass das Stoppen des Dienstes den Mount entfernt.

Lokal ausführen

Mit WG_DRYRUN=true wird kein WireGuard-Gerät angetastet:

cat > providers.json <<'EOF'
{"providers":[{"id":"google","kind":"oidc","name":"Google","oidc_issuer":"https://accounts.google.com","oidc_client_id":"xxxx.apps.googleusercontent.com"}]}
EOF
export PROVIDERS_FILE=$PWD/providers.json
export WG_ENDPOINT=vpn.example.com:51820
export CREDENTIALS_DIRECTORY=$HOME/.local/state/claimward-dev-creds
(umask 077; mkdir -p "$CREDENTIALS_DIRECTORY"; wg genkey > "$CREDENTIALS_DIRECTORY/wg-private-key")
chmod 0400 "$CREDENTIALS_DIRECTORY/wg-private-key"
export WG_DRYRUN=true LISTEN_ADDR=:8080

go run ./cmd/claimward-server

task run:dev tut dasselbe mit GitHub-Anmeldung und einem flüchtigen Schlüssel, und task dex startet ein lokales Dex, bei dem man sich anmelden kann (deploy/dev/).

Hinter TLS betreiben. Bearer-Tokens sind Zugangsdaten: Stellen Sie die API immer über HTTPS bereit, entweder mit TLS_CERT/TLS_KEY oder hinter einem Proxy, der TLS terminiert, und geben Sie dem RouteService ein Zertifikat, damit Geräte Live-Aktualisierungen der Routen erhalten.
